# AI司令部(技術名は ai-headquarters)

司令部組織の考え方を、Claude Code のサブエージェント、スキル、Hooks に当てはめた一式です。あなたが「指揮官」として目的と完了条件を示すと、調査、計画、承認、実装、点検、報告が、規律をもって回ります。陸上自衛隊の幕僚活動をモチーフにしていますが、教範どおりではありません。入れてすぐ動き、小さな仕事では重くならない設計です(確かめた環境と、まだ確かめていないことは、第11章にあります)。

> **先に読んでください**
>
> - **Node.js 22 以上が必要です(確かめ方と入れ方は、すぐ下の「まず Node.js を確かめてください」)。** Node.js が無い環境では、統制の仕組み(Hooks)が動かないため、ファイルの書き込み、Bash・PowerShell のコマンドの実行、サブエージェントの起動がすべて止まります(ファイルの読み取りや検索は止まりません)。素通りするより止まるほうを選んでいます。
> - **Hooks は、うっかりした操作を止める安全柵です。意図的なすり抜けまで防ぐセキュリティの仕組みではありません。** Hooks は完全なシェルの解析をしないので、書き方を工夫すれば、保護パスや破壊的コマンドの照合をすり抜けられます。
> - Claude Code 2.1.295 以上が必要です(Hooks の `onFailure` が使える最初の版)。端末で `claude --version` を実行すると、版を確かめられます。
> - このプラグインは、陸上自衛隊の公式な見解や監修を受けたものではありません。言葉は防衛省・陸上自衛隊などの公開資料を参考にしていますが、意味は AI の作業に合わせて使っています。出典は第14章にあります。

## まず Node.js を確かめてください

**AI司令部は、Node.js(ノード・ジェイエス)が入っていないと使えません。** 安全のための確認の仕組み(Hooks)を Node.js で動かしているためです。Node.js が無いと、確認ができないので、安全のために、ファイルの書き込み、コマンドの実行、サブエージェントの起動がすべて止まります。導入の前に、次の手順で確かめてください。

### 入っているかの確かめ方

1. 端末を開きます。Windows は「PowerShell」(スタートメニューで「PowerShell」と検索)、Mac は「ターミナル」(Spotlight で「ターミナル」と検索)です。
2. 次のように入力して、Enter を押します。

```text
node --version
```

3. 結果を見ます。
   - `v22.12.0` や `v24.11.1` のように、`v` のあとの最初の数字が **22 以上** なら、そのまま使えます。
   - 数字が 22 より小さいときは、古い版です。下の手順で入れ直してください。
   - 「認識されません」「command not found」などと出たときは、入っていません。下の手順で入れてください。

### 入れ方

1. Node.js の公式サイト(<https://nodejs.org/ja>)を開き、「LTS」(長期サポート版)と書かれた版のインストーラーをダウンロードします。
2. ダウンロードしたファイルを開き、画面の案内に従って入れます。設定は、最初から選ばれているままで構いません。
3. 開いていた端末と Claude Code を、いったんすべて閉じてから、開き直します(開き直さないと、入れた Node.js が見つかりません)。
4. もう一度 `node --version` で確かめます。

Windows で、コマンドで入れたい場合は、PowerShell で `winget install OpenJS.NodeJS.LTS` でも入れられます。

導入したあとに、書き込みやコマンドが理由も分からず止まるときも、まず Node.js が入っているかを確かめてください。

## はじめの5手順

1. Node.js が入っていることを確かめ(上の「まず Node.js を確かめてください」)、導入します(第5章)。デスクトップアプリで入れると、ユーザー全体(すべてのプロジェクト)に入ります。プロジェクト単位で入れたいときは、端末で入れます。特定のプロジェクトで止めたいときは、そのプロジェクトの `.claude/settings.local.json` の `"enabledPlugins"` に `"ai-headquarters@ai-headquarters": false` と書きます(第5章の「デスクトップアプリだけを使っている場合」の「入る範囲」)。
2. Claude Code で、新しいセッションを開きます。
3. `/ai-headquarters:mission` に、目的、完了条件、制約を添えて送ります。
4. 目標が示されたら読み、よければ「承認」とだけ入力するか、直す点を書きます。続けて計画が示されたら、同じように決心します(小規模の作業では、どちらも要りません)。
5. 結果、未解決事項、次の任務案の報告を受けます。「未解決」があれば、判断してください。

## 1. 組織の考え方

指揮官(あなた)が企図を示し、目標と計画を決心し、最終判断をします。メインセッションが幕僚長になり、あなたが決心した範囲で、各部と部隊に任務を与えます。第2部、第3部、監察と隷下部隊は、サブエージェントです(第1部と第4部はルールです)。

**幕僚**は、指揮官を補佐する役です。幕僚長(メインセッション)のもとで、第2部(intel)が調べ、第3部(plans)が案を作り、監察(inspector)が点検します。この3体は書き込みません。**隷下部隊**は、命令の範囲で実際に手を動かす部隊で、AI司令部では実装を担う unit です。

| 役職 | 役割 | 実体 | 権限 |
| --- | --- | --- | --- |
| 指揮官 | 企図を示し、目標と計画を決心し、最終判断する | あなた | 全権 |
| 幕僚長 | 任務分析、各部への割り振り、報告の取りまとめ | メインセッション | 指揮官の決心の範囲で全ツール |
| 第1部 | 任務に応じた編成とモデルの割り当て。大規模では、各行動方針を「要員と指揮官の手間」の立場から評価する | スキル `mission-analysis` の編成ルール | (ルール) |
| 第2部 | 調査を担当し、事実と根拠だけを報告する。大規模では、状況の特質を整理する | サブエージェント `intel` | 読み取りと検索のみ |
| 第3部 | 大規模で、行動方針を2〜3案作る | サブエージェント `plans` | 読み取りのみ |
| 第4部 | 作戦記録の管理。中規模以上では、使える資源を点検し、足りない資源を示します(資源の手配の提案)。大規模では、各行動方針を「作戦を支える資源」の立場から評価する | 作戦記録と運用ルール | (ルール) |
| 隷下部隊 | 命令の範囲で実装する | サブエージェント `unit` | 読み書きとコマンド実行 |
| 監察 | 実装前の計画の反対検討(大規模では、我の行動方針の分析)と、成果物の独立した点検 | サブエージェント `inspector` | 読み取りとテスト実行 |

第1部と第4部は、常に動く機能なので、エージェントにせず、メインセッションが従うルールにしています(エージェントは4体のままです)。それぞれが作戦のどこで働くかは、第2章の「AI司令部の思考過程」にあります。

### 製品の核

1. **幕僚役は書き込まない。** intel、plans、inspector は、書き込む道具を持たず、Hooks でも止めます。ツールの許可リストと Hooks の二重で守ります。
2. **小さな仕事は単独で片付ける。** 誤字修正のような作業では、サブエージェントを起動しません。大きな手続きを小さな仕事に使いません。
3. **点検は作った本人以外が行う。** unit が作ったものは、inspector が確かめます。inspector は指摘だけを返し、自分では直しません。

そのほか、受けた任務はすぐ実行せず、まず目的と完了条件を明確にします(任務分析)。中規模以上では、目標を必成目標と望成目標に分け、目標と計画のそれぞれについて、あなたの決心を求めます。大規模では、計画を1案で決め打ちせず、行動方針を比べてから推奨案を示します。

## 2. 使い方

### 作戦を始める

```text
/ai-headquarters:mission ログイン画面の初回表示を速くしたい。完了条件は…、触ってはいけないものは…
```

コマンドの名前には `ai-headquarters:` が付きます。`/ai-headquarters:mission` は、あなたしか始められません(Claude が勝手に始めることはありません)。

**企図**は、あなたが達成したいことと、その理由です。手順ではなく、目的、完了条件、制約の3つを書くと、任務分析がぶれません。書き方の例は、GitHub のリポジトリ(<https://github.com/namakemono-tech/ai-headquarters>)の `templates/CLAUDE.example.md` にあります(使う場合は、自分の CLAUDE.md に写します)。プラグインとして入れても、雛形はあなたのプロジェクトの中には置かれません。

`/ai-headquarters:mission` を使わない普段の依頼でも、セッション開始時に「まず規模を見て、中規模以上なら `mission-analysis` を使う」という案内が入るので、規模判定が効く設計です。

### 規模を指定する

最初の語に「小」「中」「大」を付けると、規模の判定を上書きできます。

```text
/ai-headquarters:mission 大 ログイン画面を作り直す
```

### 規模の目安と編成

| 規模 | 目安 | 編成 | 決心 |
| --- | --- | --- | --- |
| 小 | 変更が1〜2ファイル、調査が要らない、すぐ戻せる | メインセッション単独 | 不要 |
| 中 | 3ファイル以上、または調査が要る | intel、unit、inspector(計画はメインセッションが作成)。必成目標と望成目標を使う | 目標と計画の2回 |
| 大 | 新しいツールや構造の変更、取り消しが難しい、またはおおむね10ファイル以上 | 4体すべて。状況の特質、行動方針の分析と比較、中間報告を含む | 目標、計画、中間報告のあとの節目ごと |

迷ったら大きい側で判定します(小さい側に誤ると、決心と点検が抜けるためです)。あなたの指定が最優先です。この目安は、実機の測定で調整する予定です。

### AI司令部の思考過程

中規模以上の作戦は、次の順に進みます。幕僚長と幕僚(第1章)が案を出し、あなた(指揮官)が決心します。小規模では、任務分析のあと、メインセッションが自分で実装して報告するだけで、決心は要りません。

#### 決心の入力のしかた

- **決心**は、幕僚が示した案を、あなたが決めることです。
- 示された案でよければ、**「承認」とだけ入力**します。前後の空白と、末尾の「。」「!」を除いて、「承認」と完全に一致したときだけ承認と見なします(「承認します」「OK」は承認になりません)。選択肢の画面での回答は使いません。
- 直したいときは、直す点や自分の案を、そのまま書きます。それを決心として扱い、反映した内容が示されます。
- 承認は、そのセッションと、その時点の作戦に結び付きます。新しい作戦や別のセッションでは、あらためて承認が要ります。

#### 1. 任務分析

受けた依頼をすぐには実行せず、目的と完了条件を短く言い直し、推測で補った点、**速報事項**(起きたらすぐあなたに知らせること)、規模を示します。中規模以上では、この時点で**作戦記録**(作戦ごとの記録。`.ai-headquarters/operations/OP-001.md` など)を作ります。承認は作戦記録に結び付くので、作戦記録ができてから決心を求めます。

中規模以上では、目標を次の2つに分けます。企図の中で、あなたが分けて示してもかまいません(その場合は、それに従います)。

- **必成目標**: 必ず達成しなければならない目標です。達成できなければ任務は失敗です。原則として一つにします。複数になるときは、達成する順番(時期的順位)を付けます。
- **望成目標**: 達成することが望ましい目標です。いくつあってもよく、それぞれに優先順位と損耗限度を付けます。
- **損耗限度**: その望成目標のために使ってよい、サブエージェントの起動回数と時間(分)の上限です。上限に達したら、その望成目標を捨てて必成目標を守ります(6の「実行」)。

必成目標を原則一つにすることと、望成目標に損耗限度を付けることは、陸上自衛隊の教範ではなく、元自衛官によるビジネスへの応用の発信などを参考に取り入れました(出典は第14章)。

ふつうは、あなたが企図を伝え、幕僚がそれをもとに目標を案出します。任務分析の報告では、目標の一つ一つに、根拠が短く添えられます。依頼の文から導いた目標には「依頼の『〇〇』から」と依頼の言葉が引かれ、依頼に無く補った目標には「推測」とその理由が書かれます。あなたの企図からどう目標を導いたかを、ここで確かめてください。

あなたが企図の中で、目標の区分(必成目標、望成目標)、優先順位、損耗限度、時期的順位まで書いたときは、目標の案のすぐあとに、「あなたが書いた目標(原文)」(あなたが書いた目標、区分、損耗限度を述べた文を、文末も含めて一字も変えずに写したもの)と「あなたが書いた目標から改めた点」の欄が、この順で出ます。目標を書かずに依頼したときは、この2つの欄は出ません。あなたの区分は言い換えずに使います。ただし、規律と食い違うとき(たとえば、inspector による点検は規律なので、望成目標にできません)は区分を改め、改めた点と理由を示して、目標の決心を求めます。あなたが「テストを実行すること」を望成目標にしたときは、規律と食い違わないので、区分を改めずにそのまま扱います。あなたが示していない望成目標に、あなたの損耗限度を付け替えることはしません。

大規模では、4で行動方針を比べるときの物差し(**評価基準**)も、ここで示します。

#### 2. 目標の決心(中規模以上)

任務分析で示した目標は、このあとの計画の前提です。前提を見ないまま計画を決めることが無いよう、ここで一度止まり、あなたの決心を求めます。

- 決心すること: 必成目標と望成目標(優先順位、損耗限度、時期的順位、根拠)。あなたが目標を書いて依頼したときは、改めた点とその理由も。大規模では評価基準も。
- 入力: よければ「承認」とだけ入力します。直す点や自分の案を書いたときは、それを決心として扱い、反映した目標を示してから、計画に進みます(改めて「承認」と入力する必要はありません)。直す点が規律と食い違うときだけは、改めた点と理由が示され、もう一度決心を求められます。
- 損耗限度は、ここであなたが前もって与える裁量です。その範囲で望成目標を捨てる判断に、あなたの承認は要りません。
- 省ける場合: あなたが企図で目標をすべて示し、メインセッションが補ったものも改めたものも無いときは、すでに決心済みとして、この段階を省きます。「すべて」とは、必成目標と望成目標に加えて、すべての望成目標の優先順位と損耗限度、必成目標が複数のときの時期的順位までです。大規模で評価基準を示していないときは、省けません。省いたことと理由は、任務分析の報告と作戦記録に書かれます。
- 目標の決心を受けるまで、計画のためのサブエージェントは起動しません。

例(目標をすべて示した企図。目標の決心は省かれます):

```text
/ai-headquarters:mission 中 必成目標は、cart.js と receipt.js の金額の表示を「円」付きにすること。望成目標は、README の例も直すこと(優先1、損耗限度は、起動1回、10分)
```

#### 3. 計画

中規模では、メインセッションが計画を1案で作ります。調査が要るときは、intel(第2部)が調べます。計画には、代替案と、代替案に切り替える条件、切り替えられる最後の時点を付けます。

大規模では、計画を1案で決め打ちせず、次の4で、やり方の案を比べてから計画にまとめます。

中規模以上では、計画を作るときに、第4部として**資源の手配**をします(0.3.0)。作戦を支える資源を見つけて計画に組み込み、足りない資源を示すことです。決めるのはあなたです。

- 入っているスキルのうち、この作戦に役立ちそうなものを、名前と説明だけから、役立ちそうな候補を3つまで選び、計画書の「使う資源」の欄に、何に使うかと一緒に示します。この段階では、候補の SKILL.md を読みません(読む量を増やさず、プロジェクトの外のファイルを読む許可の確認も出さないためです)。
- 入っている資源で足りないときは、何が足りず何に困るかを示します。幕僚の判断で外を探し始めることはしません。外を探すかは、あなたが計画の決心で決めます。
- MCP のツールは、メインセッションが、読み取り系だけを使います。読み取り系か書き込み系かを名前や説明から判断できないものは使いません。
- 公開されているスキルやプラグインを入れるのはあなたです。今の作戦の計画は、入っている資源だけで立てます。作戦の途中で入れたものは、今の作戦では使わず、統制が変わった可能性が速報事項として知らされ、新しい作戦で使うことが提案されます。

#### 4. 我の行動方針の分析と比較(大規模)

**行動方針**は、任務を達成するやり方の案です。次の順で、案を作り、弱点を調べ、比べます。幕僚の起動は、intel、plans、inspector が1回ずつです。

1. intel(第2部)が、**状況の特質**を整理します。任務の特質、地形(動かせない制約)、敵、我(AI とツールの強みと弱み)、時間の5つの観点です。
   - ここでの「敵」は、自分たちでは制御できず、任務の達成に影響する外部の要因です(例: 既存の機能が想定と違う動きをする、依存パッケージの仕様が変わる、依頼の中に解釈が分かれる点がある)。
   - 敵が起こしうることを**敵の可能行動**と呼び、5つまでに絞って、最も起こりやすいものと、起きたら最も痛いものを示します。
2. plans(第3部)が、行動方針を2〜3案作ります。1案しか成り立たないときは、その理由を書きます。
3. inspector(監察)が、各案を敵の可能行動と掛け合わせ、「我の行動 → 敵の可能行動が起こす問題 → こちらの対処」の表を、案ごとに作ります。
4. メインセッションが、第1部(要員と指揮官の手間)と第4部(作戦を支える資源)の立場から各案を評価し、2で決心した評価基準で比べて、推奨案を計画書にまとめます。

「敵」を外部の要因と読むことと、第1部(要員と指揮官の手間)と第4部(作戦を支える資源)の立場から案を評価することは、元自衛官によるビジネスへの応用の発信などを参考に取り入れました(出典は第14章)。

すべての案に、必成目標を達成できなくなる弱点があるときは、推奨案を出さず、判断を仰ぎます。

#### 5. 計画の決心

計画が示されたら、決心します。大規模では、推奨案、比較の表、推奨の理由もあわせて示されます。

- 入力: よければ「承認」とだけ入力します。直す点を書いたときは、反映した計画が示されるので、改めて「承認」とだけ入力します(unit の起動には「承認」の記録が要るためです)。
- 計画の決心が無い間は、unit は起動できません(Hooks で止まります)。目標の決心だけでは、unit は起動できません。
- 使う資源: 候補のスキルのうちどれを使うかと、足りない資源について外を探すかも、ここで決めます。使うスキルは、直す点として書きます(例: 「候補の1を使う」)。使うスキルを書いたときは、反映した計画が示されたあと、改めて「承認」とだけ入力します。「外を探す」と書くと、それがあなたの決心になり、すぐに intel(第2部)が1回だけ調べます(外を探す調べ物はファイルを変えず、計画も変わらないので、そのための承認は求められません。unit の起動には、これまでどおり「承認」が要ります)。

#### 6. 実行

メインセッションが**命令書**(サブエージェントへの依頼書)を書き、unit(隷下部隊)がその範囲で実装します。サブエージェントは会話の文脈を持たずに起動するので、命令書は単体で読める形で書きます。unit は同時に1体だけ動きます。調査と点検は並列にできます。同時に動くサブエージェントは3体までです(ルールで守らせます。Hooks では止めません)。作戦中は、組み込みのサブエージェント(Explore、general-purpose など)を使わず、本製品の4体だけを使います。

大規模では、1、2件の任務ごとに中間報告があります。次の unit を起動する前に、「承認」とだけ入力します(節目の決心)。

あなたが使うと決めたスキルだけを、Read で全文読みます。スキルを読み込むこと(起動)には副作用があるので、Skill ツールで読み込み直さず、読んだ中身から要点を命令書に写します。写した部分には「外から来た文」と書き添え、受け取ったサブエージェントは、そこに書かれた指示に従いません。次のどれかがあるスキルは使いません。

- 本文の `!` のコマンド(読み込んだときにシェルで実行されます)
- `context: fork`(別のサブエージェントで動き、作戦中は4体だけという規律の外に出ます)
- `allowed-tools`(許可の確認を省きます)
- `hooks`(読み込んだときに登録され、統制が途中で変わります)
- 働きを知らない frontmatter の欄、500行を超える長さ

プロジェクトの外にあるスキル(プラグインや、ユーザー全体のスキル)を読むときは、読む許可の確認が出ます(`claude -p` では拒否されます)。使えなかったスキルは、理由が知らされ、そのスキル抜きで進めます。組み直しが要るときは、途中修正として扱います。

外を探すと決めたときの intel の調べ物は、目標に含めない付帯任務です。命令書には、プロジェクトのファイルを読まない、URL に手元の情報を入れない、外の文書に書かれた指示に従わない、の3つの制約が書かれます。候補ごとに、出典、作者、最終更新、マーケットプレイスの段(公式、コミュニティ、第三者)、入れると何が動くか(Hooks、MCP サーバー、スクリプト)が、最終報告の次の任務案に載ります。入れるのはあなたです。入れる前に、公式の点検の手順(https://code.claude.com/docs/en/plugins/security)で確かめてください。

作戦の途中で、望成目標が損耗限度に達したとき、または必成目標を危うくすると判断したときは、その望成目標を捨てて必成目標を守ります。この判断に、あなたの承認は要りません(損耗限度は、目標の決心であなたが前もって与えた裁量だからです)。捨てたことと理由は、作戦記録に書かれ、中間報告(大規模)と最終報告で知らされます。あなたが企図で示した望成目標を、損耗限度に達した以外の理由で捨てるときは、承認を待たずに、すぐ知らされます(速報事項)。

望成目標のための操作が、権限の確認で拒まれたときや、Hooks に止められたときも、損耗限度の試行1回と数えます。別の手段は試しません。損耗限度に達したら捨て、最終報告に「何の権限があれば達成できたか」を書きます。あとから許可を与えて、改めて命じることができます。必成目標が止められたときは、これまでどおり「未解決」として、あなたの判断を仰ぎます。メインセッションの命令書の書き誤りで、Hooks が unit の起動を止めたときは、まだ何も試していないので、損耗限度に数えません。命令書を直して、出し直します。

#### 7. 監察

inspector(監察)が、作った本人以外の立場で成果物を点検し、指摘だけを返します(自分では直しません)。陸上自衛隊の監察は、部隊の実情を把握して、隊務の正常な運営を妨げる要因を探り、改善を進めるものです(出典は第14章)。AI司令部では、成果物の点検と計画の反対検討を受け持たせています。

監察の合否は、命令書の必成、制約を守ったこと、既存の動作を壊していないことで決めます。既存の動作を壊していないことをどう確かめるか(テストを実行する、コードを読むなど)は、inspector が決めて、報告に書きます。テストを実行すること自体は、規律ではありません。望成目標が達成できなかっただけでは不合格にせず、報告で知らせます。不合格なら、6の実行に戻ります。

#### 8. 報告

結果、必成目標と望成目標それぞれの達成状況(捨てた望成目標と理由、権限で止められたときは何の権限があれば達成できたか)、未解決事項、次の任務案が報告されます。作戦記録が保存されるまで完了としません。「未解決」があれば、判断してください。

#### 決心の回数

| 規模 | 決心の回数 |
| --- | --- |
| 小 | なし |
| 中 | 目標と計画の2回(目標の決心を省けるときは1回) |
| 大 | 目標、計画、中間報告のあとの節目ごと(目標の決心を省けるときは計画から) |

0.1.x では、中規模の承認は計画の1回でした。0.2.0 では、中規模でも大規模でも、目標の決心の1回が増えます。あなたが企図で目標をすべて示し、補ったものも改めたものも無いときは省かれ、省いたことと理由が報告されます。

### 命令書と報告の型

サブエージェントは会話の文脈を持たずに起動するため、命令書は単体で読める形にします(任務番号、企図、任務、状況、変更してよいファイル、制約、完了条件、報告要領)。報告は、任務番号、結論、根拠、未解決・懸念、推測を、この順で返します(unit は実施内容も)。中規模以上では、命令書の完了条件を必成と望成に分けて書き、unit と inspector は、それぞれの達成状況を「目標の達成」の欄で返します。計画書には、0.3.0 から「使う資源」の欄があります。詳しくは `skills/mission-order/SKILL.md` にあります。報告に「未解決」があれば、メインセッションは勝手に補わず、あなたに判断を仰ぎます。

## 4. Hooks が確認して止めること

Hooks は自動でコマンドを実行します。何を確認して何を止めるかを、すべて書きます。

### 止め方の2種類

- **サブエージェント:止めます**(拒否)。
- **メインセッション(あなたとの対話):確認を出します**(あなたが判断します)。あなたが自分で頼んだ操作(`rm -rf node_modules` など)まで止まると、許す道が無くなるためです。
- 例外として、次の3つは、メインセッションでも**止めます**。承認の記録や設定、作戦の証拠を、Claude が書き換えたり消したりできないようにするためです。
  - `.ai-headquarters/config.json` への書き込み
  - `.ai-headquarters/state/` の中のファイルへの書き込み
  - 作戦記録の削除と、丸ごとの上書き(Write)

メインセッションかどうかは、Hooks の入力に `agent_id` があるかで見分けます。agent teams の仲間のセッションも `agent_id` を持つので、サブエージェントとして扱います。

Hooks が止めたとき、unit と inspector は、別の手段(シェルでの書き込みなど)で同じことを試さず、「未解決」として報告するよう決められています。

### 役ごとの制限

実行中のエージェントの種類(`agent_type`)を見て、次のとおり制限します。プラグイン同梱のエージェントでは、定義ファイルに書いた Hooks が無視されるため、プラグイン全体の Hooks で行います。

| 役 | 制限 |
| --- | --- |
| intel、plans | 書き込み系のツール(Edit、Write など)と、Bash・PowerShell の実行を止める |
| inspector | 書き込み系のツールを止める。Bash・PowerShell は**許可リスト**に合うものだけを通す(下の表) |
| unit | 書き込みは、命令書の【変更してよいファイル】の範囲だけ(下の「unit の範囲」) |
| intel、plans、unit、inspector 共通 | ほかのサブエージェントを起動することを拒否する |
| 種類を判別できないもの(組み込み、他のプラグインのエージェント) | 役ごとの制限はかけない。保護パス、破壊的コマンド、作戦記録・設定・状態の保護だけを当てる(他のプラグインを壊さないため) |

**inspector の Bash・PowerShell の許可リスト**

コマンドの中身から書き込みを見抜く方式は漏れが出るため、「通してよいものだけを通す」方式にしています。

| 種類 | 通すもの |
| --- | --- |
| テスト | 既定で `npm test`、`pnpm test`、`yarn test`、`node --test`、`pytest`、`go test`、`cargo test`。`-` で始まらない引数(ファイルのパスやテスト名)は付けてよい。`-` で始まるオプションは、設定ファイルに書いたものだけ通す。プロジェクト固有のテストコマンドも設定ファイルで足せる |
| 読み取り専用の git | `git diff`(`--stat`、`--name-only`、`--name-status`、`--cached`、`--staged`)、`git status`(`-s`、`--short`、`--porcelain`)、`git log`(`--oneline`、`-n`、`--stat`、`--format`)、`git show`(`--stat`、`--name-only`) |

- 許可リストどおりの `git diff`、`git log`、`git show` は、Hooks が `--no-ext-diff --no-textconv` を付け足したうえで `allow` を返し、通常の確認を飛ばして実行します。
- `-` で始まらない引数(コミットやパス)は通します。
- `git` の直後には、上の4つのサブコマンドが来なければなりません。`-c`、`-C`、`--git-dir`、`--work-tree`、`--exec-path` など、間に置くオプションはすべて止めます。
- `git diff`、`git log`、`git show` には、Hooks が `--no-ext-diff --no-textconv` を付け足してから実行させます(外部のプログラムが動くのを防ぐため)。
- コマンドをつないだり、入出力を切り替えたりする記号(`&&`、`||`、`;`、`|`、`&`、`>`、`>>`、`<`、`$(`、バッククォート、改行)を含むコマンドは止めます。引用符の中にも当てるので、`--format="%h|%s"` も止まります。
- 読み取り系のコマンドでも、オプション次第で、ファイルを書いたり(`--output`)、外部のプログラムを動かしたり(`--ext-diff`、`--textconv`、`-c`)できるため、許すオプションを限っています。

### 保護パス

書き込みの前にパスを確認します。`.env` などの秘密のファイルは、シェルでの読み取り(`cat` など)も確認の対象にします。**Read ツールでの読み取りは Hooks を通らないため、止まりません**(Read、Grep、Glob は Hooks の対象外です)。表の「止める」は、第4章の止め方に従います(メインセッションには確認、サブエージェントには拒否)。文字列の部分一致は使いません(`process.env` や `.env.example` まで止めないためです)。

| 保護するもの | 照合の単位 | シェルでの読み取り(`cat` など) |
| --- | --- | --- |
| `.env`、`.env.*`(ただし `.env.example`、`.env.sample`、`.env.template` は除く) | ファイル名 | 止める |
| `*.pem`、`*.key`、`*.p12`、`*.pfx`、`*.jks`、`*.keystore`、`id_rsa*`、`id_ed25519*`、`.npmrc`、`.netrc`、`secrets.toml` | ファイル名 | 止める |
| `credentials`、`credentials.json`、`credentials.yml`、`credentials.yaml`、`secrets.json`、`secrets.yml`、`secrets.yaml`、`.secrets` | ファイル名(`credentialsService.ts` のような普通のソースは止めません) | 止める |
| 設定ファイルで追加したパス | 設定ファイルの書き方による | 止める |
| `.ai-headquarters/config.json`、`.ai-headquarters/state/` の中 | プロジェクトの最上位からの相対パス | 通す |
| `.claude/settings.json`、`.claude/settings.local.json`、`.claude/hooks/ai-headquarters/` の中 | プロジェクトの最上位からの相対パス | 通す |

最後の2行は、書き込みだけを止めます。読み取りは通します。

パスは、照合の前に、プロジェクトの最上位からの相対パスに直し、区切りを `/` にそろえます。Windows と Mac では、大文字・小文字の違いを無視します(Linux は区別します)。

操作の対象が、保護された場所の上位のフォルダ(`.ai-headquarters/`、`.claude/` など)のときも、一致と見なします。`mv .ai-headquarters x` のように、フォルダごと動かして保護をすり抜けるのを防ぐためです。

**追加と除外(設定ファイル)**: 書き方は `.gitignore` に近い形です。

- `/` を含まない項目(例:`*.secret`)は、ファイル名として、どのフォルダでも当てます。
- `/` を含む項目は、プロジェクトの最上位からの相対パスとして当てます。`**` で何段のフォルダにも当てられます。
- 末尾が `/` の項目は、フォルダとして扱い、中のすべてのファイルに当てます。
- 設定ファイル、状態ファイル、作戦記録の保護は、「除外」では外せません。

### 破壊的なコマンド

Bash と PowerShell の実行前に、次のものを照合します(メインセッションには確認、サブエージェントには拒否)。

- `rm -r`、`rm -rf`(パスを問いません。`rm -fr`、`rm -R`、`rm --recursive` も同じ扱い)
- `git push --force`、`git push -f`、`git push --force-with-lease`
- `git push origin +main`(`+` を付けた強制)、`git push --force-if-includes`
- `git reset --hard`、`git clean -f`、`git checkout -- .`、`git checkout .`、`git restore .`、`git branch -D`(`git branch --delete --force` も同じ扱い)
- `git stash -u`、`--include-untracked`、`-a`、`--all`(未追跡の設定や `.env` をまとめて退避するため)
- `Remove-Item -Recurse`(別名の `rm`、`del`、`ri`、`rd`、`rmdir` を含む)、`rd /s`、`del /s`
- `format`、PowerShell の `Format-Volume`(コマンド名として使った場合)、`find ... -delete`

コマンドを `&&`、`||`、`;`、`|`、`&`、`(`、`$(`、バッククォート、改行で区切り、各部分の先頭の語と引数で照合します。`cmd /c`、`bash -c`、`sh -c`、`pwsh -c`、`powershell -Command`、`sudo`、`env`、`xargs` は「包み」として、後ろのコマンドを取り出して照合し直します。`git log --format=...` や `npm run format` のように、語の一部に含まれるだけのものは止めません。

### 作戦記録、設定、状態の保護

- 作戦記録(`.ai-headquarters/operations/`)の削除と、Write での丸ごとの上書きを止めます(メインセッションでも)。部分的な更新(Edit)は通します。削除と移動のコマンド(`rm`、`del`、`Remove-Item`、`mv`、`move`、`Move-Item`)の引数に `.ai-headquarters/operations/` があれば止めます。
- 既存の作戦記録を、シェルで丸ごと上書きすることも拒否します(メインセッションでも)。`>` でのリダイレクト、`Set-Content`、`cp`、`mv`、`sed -i`、`tee`(`-a` なし)が対象です。追記(`>>`、`Add-Content`、`tee -a`)は通します。
- 作戦記録があるとき、作戦記録を巻き込みうる `git clean -fdx`(`-d`、`-x`)は、メインセッションでも拒否します。
- サブエージェントによる `.ai-headquarters/` への書き込みを止めます。
- 設定ファイルと状態ファイルへの書き込みを止めます(メインセッションでも)。

### Claude Code の設定(`.claude/`)の保護

`.claude/settings.json`、`.claude/settings.local.json`、`.claude/hooks/ai-headquarters/` と、その親のフォルダ(`.claude/`、`.claude/hooks/`)を対象にした操作も、一致と見なします(メインセッションには確認、サブエージェントには拒否)。対象の操作は、削除、移動、名前の変更、`git checkout`、`git restore`、`cp`・`rsync`・`Copy-Item` などの書き込み先です。`git restore --staged` のようにワークツリーを変えないものは通します。

`.claude/hooks/ai-headquarters/` は、プラグインとして入れた場合は使わないフォルダですが、同じ名前のフォルダが作られたときに備えて守っています。

### プラグインと MCP のコマンド

プラグインと MCP の状態を変えるコマンドは、サブエージェントでは止め、メインセッションには確認を出します(0.3.0)。作戦の外でも、ほかのプラグインのエージェントにも当てます。入れたものの Hooks や MCP サーバーは利用者の権限で動き、AI司令部自身を外す(`disable`、`uninstall`)こともできるためです。

- `claude plugin`(別名 `claude plugins`)のサブコマンドのうち、`list`、`details`、`validate`、`help` 以外のすべて(`install`、`i`、`uninstall`、`remove`、`enable`、`disable`、`update`、`init`、`new`、`eval`、`configure` など)。`marketplace` は `list`、`help` 以外(`add`、`update`、`remove` など)
- `claude mcp` のサブコマンドのうち、`list`、`get`、`help` 以外のすべて(`add`、`add-json`、`remove` など)
- `claude` に `--plugin-dir`、`--mcp-config`、`--dangerously-skip-permissions` を付けた入れ子の起動

### スキル、エージェント、MCP の登録への書き込み

プロジェクトの `.claude/skills/`、`.claude/agents/`、`.mcp.json` への書き込みは、次のとおりです(0.3.0)。

- unit: 命令書の【変更してよいファイル】にはっきり書かれているときだけ書けます。`.claude/skills/**`、`.claude/skills/a/SKILL.md`、`.mcp.json` のように、そのパスを書いたときです。`**`、`.claude/**`、`*.json` のような広いグロブにたまたま含まれるだけでは、書けません。命令書は、あなたが計画の決心で認めた範囲から作るので、あなたが認めたときだけ書ける形になります。
- ほかのサブエージェント(ほかのプラグインのエージェントを含む): 止めます。
- メインセッションは止めず、確認も出しません。メインセッションが書くものは、あなたが会話の中で見ているためです。スキルを作るプロジェクトでも、そのまま使えます。
- シェルのコマンドで、この3つを書き換えるもの(削除、移動、コピーの書き込み先、リダイレクトなど)は、サブエージェントでは止めます。unit が書くときは、Edit か Write を使います。

### 作戦中のスキルの読み込み

作戦中に、AI司令部の3つのスキル以外を Skill ツールで読み込もうとすると、メインセッションには確認を出し、サブエージェントでは止めます(0.3.0。bypassPermissions では止めます)。AI司令部の3つのスキルは、mission、mission-analysis、mission-order です。

- 理由: Skill ツールで読み込むと、そのスキルの埋め込みのコマンドの実行、`context: fork` による別のサブエージェントの起動、`hooks` の登録が起こりえます。資源の手配の決まりでは、候補のスキルは Skill ツールで読み込まず、あなたが使うと決めたものだけを Read で読んで命令書に写すので、作戦中にほかのスキルを Skill ツールで読み込む正当な場面はありません。
- 作戦中かの見分け方: メインセッションが作戦記録を書くと、Hooks がそのセッションと作戦番号を記録します。そのセッションで、最新の作戦記録の「## 結果」の次の行が「未完了」のあいだを、作戦中とします。作戦を終えて報告するときに、この行は結果に書き換えられます。
- 作戦の始まり: mission か mission-analysis が読み込まれたとき、または /ai-headquarters:mission で始めたときから、作戦記録ができる前でも、作戦中と同じく確認を出します(作戦記録を作る前に、`context: fork` のスキルが読み込まれて動いたことがあったためです)。始まりの記録は、プロジェクトではなく、OS の一時フォルダ(`ai-headquarters` という名前のフォルダ)に置きます。
- 作戦の始まりの終わり方: mission-analysis が読み込まれたあとは、任務分析の途中の質問にあなたが答えても終わらず、次のどれかで終わります。/ai-headquarters:mission は最初に mission-analysis を読み込むので、ふつうはこの終わり方になります。
  - 作戦記録ができたとき。そのあとは、作戦記録による見分け方に引き継がれます。
  - メインセッションが、プロジェクトの中の `.ai-headquarters/` の外のファイルを書き換え始めたとき。中規模以上では計画の決心までそこを変更しないので、小規模と判断して実装に入ったとみなします。
  - 始まってから、あなたの発言が3回目になったとき。小規模と判断して、ファイルを書き換えずに終わった作業でも、確認が出続けないための上限です。サブエージェントの報告の知らせは、あなたの発言として数えません。
  - /ai-headquarters:mission と打っただけで、mission-analysis がまだ読み込まれていないときは、あなたの次の発言で終わります。
- これは確認であって、拒否ではありません(メインセッションの場合)。作戦にならなかった作業(小規模と判定された依頼など)でも、確認が出ることがあります。mission-analysis が読み込まれた作業では、ファイルの書き換えが始まるか、あなたの3回目の発言までのあいだです。そのスキルを使ってよければ、許してください。
- 作戦の外では止めません。作戦を始めていないセッション、別のセッション、結果を書き終えた作戦、作戦の始まりが上のとおり終わったあとは、ほかのスキルをいつもどおり使えます。
- あなたが `/名前` と打って呼ぶスキルは、止めません(Skill ツールを通らないためです)。

### unit の範囲

unit を起動するときに、命令書の【変更してよいファイル】を記録します。unit が Edit・Write を使うたびに、その範囲と照合し、範囲外なら止めます。範囲の中なら、新しいファイルを作ってかまいません。欄が無いとき、読み取れないときは、unit の起動を止めます。その理由として、mission-order スキルを読み込み、型の見出しどおりに命令書を書き直すよう、メインセッションに伝えます。シェル(Bash・PowerShell)には範囲の照合をかけません。かけると、テストやビルドまで止まってしまうためです。

### 承認の関門

あなたの「承認」の発言を、目標の決心と計画の決心に分けて記録し、計画の決心が無い間は unit の起動を止めます。目標の決心として記録するか計画の決心として記録するかは、迷ったら目標の決心の側に倒します。計画の決心として記録するのは、同じセッションの同じ作戦で目標の決心がすでに記録されているとき、または作戦記録の「目標の決心」の欄が「修正:」か「省略:」で始まるときだけです。作戦記録が1つも無いときに「承認」と書かれても、記録しません(小規模の作業で `.ai-headquarters/` を作らないためです)。

### unit は同時に1体

unit の「予約」を、すでにあれば失敗する作り方で書き、書けなければ起動を止めます。同じ応答で2体の unit が呼ばれても、片方だけが通ります。実行中の記録は、別のセッションのものと、30分たったものを無効と見なします(中断や異常終了で、unit が二度と起動できなくなるのを防ぐため)。

実装を並列にしない理由は、同じファイルを触る作業が衝突するのを防ぐためと、起動した unit を、どの命令書の unit か Hooks が結び付ける手段が、いまは無いためです。

### 報告の確認

サブエージェント(本製品の4体だけ)が報告を返すときに、必須の見出し(【任務番号】【結論】【根拠】【未解決・懸念】【推測】。unit は【実施内容】も)があるかを確かめます。欠けていれば1回だけ差し戻して書き直させ、2回目は警告を付けて通します(何回でも差し戻すと、作業が止まってしまうため。実際に書き直されるかは、実機で確かめる途中です)。中身の正しさは確かめません。

### Hooks が動かなかったとき

- `hooks/guard.js` の **PreToolUse の登録**には、スクリプトが起動できない、異常終了した、時間切れになったときも、元の操作を**止める側に倒す** `"onFailure": "block"` を付けてあります。
- `guard.js` の SubagentStart の登録には付けていません(unit の予約を「実行中」に切り替えるだけの処理で、動かなくても予約は2分で期限が切れます)。
- 報告の確認、承認の記録、セッション開始の案内には付けていません(動かないときに、報告の受け渡しやあなたの発言まで止めないため)。10秒で時間切れになり、そのまま先へ進みます。

### 権限モードごとの確認の振る舞い

メインセッションへの「確認」は、Claude Code の権限モードで変わります。

| 権限モード | メインセッションへの確認の出方 |
| --- | --- |
| default、acceptEdits | 確認が出る |
| auto | 確認が出る(自動の判定役は使われない) |
| bypassPermissions | Hooks は確認の代わりに拒否を返す(確認の画面が出ないため) |
| dontAsk、`-p` での実行 | Hooks の確認は、拒否になる。ただし、Claude Code 自身が重要な場所の削除(rm -rf など)として扱うものは、確認の画面が出ることがある(実機で観測) |

ほかのプラグインの `PermissionRequest` の Hooks が、この確認に自動で答えてしまう場合があります。

## 5. 導入

Claude Code を、Claude のデスクトップアプリ(「Code」タブ)だけで使っていて、端末(ターミナル)では使っていない場合は、下の「デスクトップアプリだけを使っている場合」の手順で、画面の操作だけで入れられます。

### 端末で入れる場合

プロジェクト単位(`--scope project`)で入れるのを標準とします。次のコマンドは、**端末(ターミナル)で**、対象のプロジェクトの最上位で実行します。

端末は、開いた直後はホームのフォルダにいます。先に、`cd` でプロジェクトのフォルダへ移ってください。次は、プロジェクトが `D:\projects\myproject` にある場合の例です(パスは、Windows ではエクスプローラーのアドレス欄から、Mac では Finder でフォルダを端末へドラッグすると得られます)。

```text
cd "D:\projects\myproject"
```

移ったら、`pwd`(Windows の PowerShell でも使えます)で、今いるフォルダがプロジェクトのフォルダであることを確かめてから、次のコマンドを実行します。

GitHub で公開しているものを、次の2つのコマンドで入れます。

```text
claude plugin marketplace add namakemono-tech/ai-headquarters --scope project
claude plugin install ai-headquarters@ai-headquarters --scope project
```

GitHub のリポジトリを丸ごとダウンロード済みの場合は、1つ目のコマンドの `namakemono-tech/ai-headquarters` を、そのフォルダ(`.claude-plugin/` があるフォルダ)のパスに置き換えてください。2つ目は同じです。この場合、更新するときは、先にそのフォルダの中身を新しい版に入れ替えてから、下の「更新のしかた」を行います。

**SSH の鍵を GitHub に設定していない場合**:1つ目のコマンドは、まず SSH で取得を試し、失敗すると自動で HTTPS で取り直します(「SSH clone failed, retrying with HTTPS」と表示されます)。公開しているリポジトリなので、HTTPS での取得にログインは要りません。それでもうまくいかない場合は、1つ目のコマンドを、HTTPS の URL を指定する次の形に置き換えてください。2つ目は同じです。

```text
claude plugin marketplace add https://github.com/namakemono-tech/ai-headquarters.git --scope project
```

**入ったことの確かめ方**:Claude Code で、そのプロジェクトの新しいセッションを開き、`/agents` で `ai-headquarters:intel`、`ai-headquarters:plans`、`ai-headquarters:unit`、`ai-headquarters:inspector` の4体が出ること、`/` を入力したときの一覧に `/ai-headquarters:mission` が出ることを確かめます。

**利用者全体(`--scope user`)に入れた場合に起きること**:

- すべてのプロジェクトで Hooks が動きます。保護パスと破壊的コマンドの確認、サブエージェントの制限がかかります。
- すべてのプロジェクトで、セッション開始時に「小規模ではサブエージェントを使わない」という案内が入ります。
- 全体の CLAUDE.md と衝突しやすくなります(第8章)。

### デスクトップアプリだけを使っている場合

Claude Code を、Claude のデスクトップアプリの「Code」タブだけで使っている場合も、端末(ターミナル)を使わずに、画面の操作だけで入れられます。次の手順は、Windows のデスクトップアプリの日本語の画面で確かめたものです。画面の表記は、アプリの版や表示の言語で変わることがあります。

**入れ方**

1. 左のメニューの「プラグイン」を開きます。
2. 右上の「追加」の ▼ を押し、「マーケットプレイスを追加」を選びます。
3. 「リポジトリから追加」を選びます。「URL」の欄に `namakemono-tech/ai-headquarters` と入力し、「同期」を押します。欄の下に、手元のリポジトリの候補が出ることがありますが、それは選びません。
4. 同期すると、そのまま画面に AI司令部が出ます。「作成者: ナマケモノテック」と説明文が並び、右に「このコンピューターに追加」があります。
5. 「このコンピューターに追加」を押すと、「プラグイン「AI司令部」には、コードを実行するコンポーネントが含まれている可能性があります」という確認が出ます。「お使いのコンピューターで実行されるセッションでは、許可を求めずにそのコンピューター上でコードを実行する可能性があります。」「信頼できる人が作成したプラグインのみをオンにしてください。」と書かれ、「キャンセル」と「続ける」があります。AI司令部は、統制のために Hooks で Node.js のスクリプトを動かすので、この確認が出ます。
6. 「続ける」を押すと、「追加済み」と版の番号(v0.1.1 など)が出ます。これで入っています。

同じマーケットプレイスがすでに追加されている場合も、同じ手順で、同期のあとに AI司令部が出て、入れられます。

**入ったことの確かめ方**

- 設定の「プラグイン」の一覧の「その他のプラグイン」に、「AI司令部」が「ローカルにインストール済み」「提供元:ナマケモノテック」として出ます。
- 新しいセッションを作り、入力欄に `/mi` と入力します。`ai-headquarters:mission`、`ai-headquarters:mission-order`、`ai-headquarters:mission-analysis` の3つが出れば、使えます。
- AI司令部を開いた画面では、名前の下に「開発者不明」と出ることがあります。一覧の「提供元:ナマケモノテック」とは違いますが、別のマーケットプレイスから入れた Codex(提供元:OpenAI)を開いても、同じように出ました。アプリの表示によるもので、AI司令部の設定の誤りではないと考えています。

**入る範囲**

デスクトップアプリで入れると、入れる範囲を選ぶ項目は出ず、ユーザー全体(このパソコンのすべてのプロジェクト)に入ります。入れたあと、別のプロジェクトのセッションでも、`/mi` で3つのスキルが出ました。すべてのプロジェクトで Hooks が動きます(上の「利用者全体(`--scope user`)に入れた場合に起きること」)。

- **プロジェクト単位で入れたいとき**:デスクトップアプリではなく、上の「端末で入れる場合」の手順で入れます。1人で使うなら `--scope local`、git で共有してチームで使うなら `--scope project` にします。
- **特定のプロジェクトで止めたいとき**:そのプロジェクトの `.claude/settings.local.json` に、次のように書きます。ほかの設定がすでにあるときは、その中に `"enabledPlugins"` を足します。公式の文書によると、プロジェクトのローカルの設定は、ユーザー全体の設定より優先されます。止めたフォルダのセッションでは、`/mi` と入力しても、AI司令部の3つのスキルが出ません。ほかのプロジェクトのセッションでは、3つとも出ます。こうして、止まったことを確かめられます。

```json
{
  "enabledPlugins": {
    "ai-headquarters@ai-headquarters": false
  }
}
```

**そのほかの入れ方**:端末で入れたプラグインは、同じパソコンのデスクトップアプリのセッションでも使えます(端末とデスクトップアプリは同じ設定ファイルを読むため)。

**使えないセッション**:クラウドのセッションと WSL のセッションでは、プラグインを使えません(公式の文書)。

**Windows で、Node.js が見つからないと言われたとき**:デスクトップアプリは、PowerShell のプロファイルを読みません。Node.js を公式のインストーラーか `winget` で入れていれば、この問題は起きません。PowerShell のプロファイルで PATH を足して Node.js を使えるようにしている場合は、Windows の環境変数(ユーザーまたはシステム)の PATH に Node.js の場所を足し、デスクトップアプリを開き直してください。

出典(いずれも Anthropic の公式の文書):

- [Install and manage plugins](https://code.claude.com/docs/en/discover-plugins)(入れる範囲と記録される設定ファイル、範囲ごとの設定の優先順位、端末とデスクトップアプリが同じ設定ファイルを読むこと)
- [Desktop application](https://code.claude.com/docs/en/desktop)(「Install plugins」の節と、Windows の PATH の注意)
- [Plugin manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference)(画面に出る名前 `displayName`)

### 更新のしかた

AI司令部の手直しは、版(`.claude-plugin/plugin.json` の `version`)を上げて公開します。すでに入れている場合、手直しは自動では届きません。公式の文書によると、外部のマーケットプレイスは、初めは自動更新が無効だからです。次の手順で、手で更新してください。

**デスクトップアプリ**(Windows のデスクトップアプリの日本語の画面で確かめた手順です)

1. 左のメニューの「プラグイン」を開きます。
2. 右上の「追加」の ▼ を押し、「マーケットプレイスを管理」を選びます。
3. `ai-headquarters` の行の「…」を押し、「アップデートを確認」を選びます。行の「最終更新」の日時が新しくなり、画面の右下に「マーケットプレイスを更新しました。」と出ます。
4. 「完了」で閉じます。左のメニューの「プラグイン」の画面で、「マイプラグイン」の右の「すべて表示」を押し、「マイプラグイン」の画面を開きます。その中の「その他のプラグイン」にある AI司令部を開きます。開いた画面の右上には「追加済み」と「更新」があります。新しい版が無いときは、「更新」が薄い色で押せません。手順3のあとは、「更新」が押せるようになっています。「更新」を押し、画面の右下に「0.1.1 から 0.2.0 に更新しました。」のような知らせが出れば、更新できています。そのあと、「更新」はまた薄い色に戻ります。(0.2.0 への更新では、説明文も新しいものに変わりました。)
5. 新しいセッションを開いて使います。入力欄に `/mi` と入力し、`ai-headquarters:mission` の説明が「報告までの10段階」になっていれば、0.2.0 が入っています。

**「アップデートによりローカルの変更が上書きされます」と出たとき**:手順4で「更新」を押すと、この確認が出ることがあります。本文は「2 個のファイルがローカルで変更されており、この更新により上書きされます。」で、`.in_use\16072`、`.in_use\25528` のようなファイルが並び、「キャンセル」と「強制的にアップデート」があります。このとき、プラグインのファイルは書き換えていませんでした。私たちの検証では、ほかのセッションで作戦を動かしていないことを確かめてから「強制的にアップデート」を押し、問題なく更新できました。

**入れたあとに AI司令部を探すとき**:左のメニューの「プラグイン」の検索欄に `ai-headquarters` と入力し、「すべての結果を表示」を押すと、「マイプラグイン」の中に出ます。「AI司令部」と日本語で入力したときは、候補に出ません。また、入れる前は、追加したマーケットプレイスのプラグインは、検索欄では出ません。

手順3をしないと、手順4の「更新」は押せません。アプリが新しい版を知らないためです。また、「マーケットプレイスを管理」の「削除」は押さないでください。画面の説明のとおり、マーケットプレイスを削除すると、そこから入れたプラグインもアンインストールされます。

**端末**:対象のプロジェクトの最上位で、次の2つを実行します。1つ目でマーケットプレイスの写しを新しくし、2つ目でプラグインを更新します。2つ目の `--scope` は、入れたときの範囲に合わせます。終わったら、Claude Code を起動し直します。

```text
claude plugin marketplace update ai-headquarters
claude plugin update ai-headquarters@ai-headquarters --scope project
```

デスクトップアプリで入れた場合は、ユーザー全体に入っているので `--scope user` にします。(端末での更新は、まだ確かめていません。)

### 取り除き方

- **デスクトップアプリ**:左のメニューの「プラグイン」の画面で、AI司令部の行の右の「…」を押し、「削除」を選びます(「アンインストール」ではありません)。「AI司令部を削除しますか?」「Claude はこれを使用しなくなります。後で再度追加できます。」という確認が出て、「キャンセル」と「削除」があります。「削除」を押すと、画面の右下に「AI司令部が削除されました。」と出ます。このとき、マーケットプレイスは消えず、「マーケットプレイスを管理」の一覧に `ai-headquarters` が残ります。
- **端末**:対象のプロジェクトの最上位で、次を実行します。`--scope` は、入れたときの範囲に合わせます(更新のときと同じです)。この手順は、まだ確かめていません。

```text
claude plugin uninstall ai-headquarters@ai-headquarters --scope project
```

取り除いても、作戦記録や設定を置いた `.ai-headquarters/` フォルダは、プロジェクトに残ります。要らなければ、自分で消してください。

## 6. 作業対象のプロジェクトに作られるもの

どれも、中規模以上の作戦で、初めて必要になったときに作ります。小規模の作業や普段の依頼では作りません。

| 場所 | 中身 |
| --- | --- |
| `.ai-headquarters/operations/` | 作戦記録(`OP-001.md` のような、作戦ごとのファイル)。保存期間は定めず、削除はあなたが行います |
| `.ai-headquarters/config.json` | 設定ファイル。あなたが手で編集します。無くても既定値で動きます |
| `.ai-headquarters/state/` | Hooks が使う状態(承認の記録、unit に許したファイル、unit の実行中の記録、報告の差し戻しの回数、作戦中のセッションの記録) |

**git で管理するか**は、あなたが決めます。プラグインは `.gitignore` を書き換えません。判断の材料は次のとおりです。

- 作戦記録:残すと、後から経緯を追えます。チームで共有するなら管理するほうが便利です。個人の作業メモなら、管理しなくてもかまいません。
- 設定ファイル:保護パスや許可するテストコマンドは、プロジェクトの決まりなので、管理して共有するのが自然です。
- 状態:セッションごとの一時的な記録で、共有しても意味がありません。管理しないほうが無難です(`.ai-headquarters/state/` を `.gitignore` に書きます)。

## 7. 設定ファイル

`.ai-headquarters/config.json` で、保護するパスと、inspector に許すコマンドを調整します。例は、GitHub のリポジトリの `templates/config.json` にあります。

```json
{
  "protect": {
    "add": ["private/**"],
    "exclude": ["test/fixtures/dummy.pem"]
  },
  "inspector": {
    "testCommands": ["python -m pytest"],
    "allowedOptions": ["-q"]
  }
}
```

| 項目 | 意味 |
| --- | --- |
| `protect.add` | 保護パスに足すもの(書き方は第4章) |
| `protect.exclude` | 既定の保護パスから外すもの(設定ファイル、状態ファイル、作戦記録は外せません) |
| `inspector.testCommands` | inspector に許すテストコマンドの追加 |
| `inspector.allowedOptions` | inspector のテストコマンドに許す、`-` で始まるオプション |

**`testCommands` に、`make` のような汎用の実行コマンドを書かないでください。** テストコマンドは「前置き」として照合し、その後ろの語は通します。`make test` と書くと、inspector が `make test install` のように、任意のターゲットを動かせてしまいます。`python -m pytest` のように、後ろに続く語がテストの絞り込みにしかならないものだけを書いてください。

設定ファイルは、あなたが自分で、メモ帳などのテキストエディタで開いて編集してください(Hooks は、Claude による書き込みを止めます)。`.ai-headquarters` のようにドットで始まるフォルダは、Mac の Finder では見えません。Finder で `Command + Shift + .` を押すと、表示されます。

## 8. 全体の CLAUDE.md との衝突

あなたの全体の CLAUDE.md(`~/.claude/CLAUDE.md`)の方針と、衝突することがあります。たとえば「作業は常にサブエージェントに任せる」と書いていると、「小規模ではサブエージェントを使わない」という案内とぶつかります。Claude Code では、全体とプロジェクトの CLAUDE.md がぶつかったとき、どちらが優先されるかは決まっていません。本製品は CLAUDE.md に依存しませんが、衝突すると、小さな仕事でも重くなることがあります。

対処は、効き目の確かな順に、次の3つです。

1. **全体の CLAUDE.md に、例外を書き足す。** 「AI司令部を入れたプロジェクトでは、その編成ルールに従う」と書きます。最も確実です。
2. **プロジェクトの CLAUDE.md に、同じ趣旨を書く。** 優先は保証されません。
3. **プロジェクトの `.claude/settings.local.json` の `claudeMdExcludes` で、全体の CLAUDE.md を、そのプロジェクトでだけ読み込まないようにする。** 全体の CLAUDE.md のほかの規則も、そのプロジェクトでは効かなくなります。

   ```json
   {
     "claudeMdExcludes": ["**/.claude/CLAUDE.md"]
   }
   ```

   書き方の例です。全体の CLAUDE.md を除外できるかは、公式の説明に明記がなく、実機で確かめる途中です。プロジェクト自身の `.claude/CLAUDE.md` も巻き込むため、そのまま使わず、自分の環境の絶対パス(例:`<ホームフォルダ>/.claude/CLAUDE.md`)に直してください。

## 9. Agent Teams を使わないでください

Agent Teams(実験機能)を有効にしていると、サブエージェントへのスキルの事前読み込みが効かなくなり、命令書と報告の型が届きません。本製品は Agent Teams を使いません。有効にしている場合は、AI司令部を使うときだけ無効にしてください。

## 10. 限界

### 統制(Hooks)の限界

- **Hooks は安全柵であり、セキュリティの仕組みではありません。** 完全なシェルの解析はしないので、すり抜けは残ります。
- 破壊的コマンドは、禁止リスト方式です。リストに無い書き方は止まりません。
- シェルのコマンドの文字列で保護パスを照合する方式は、完全ではありません。変数の展開、`eval` の中の組み立て、シンボリックリンク、8.3 形式の短い名前は解決しません。
- 行き先の分からない `cd` の後は、パスの末尾の形で照合するため、`state/` や `config.json` という名前の普通のファイルを巻き込むことがあります。`bash <<EOF` のようにシェルへ渡すヒアドキュメントは本文も見るため、過検出がありえます。
- 親のフォルダを対象にした操作の検出が、外れる書き方が残ります(`tar -x -C .claude`、`unzip -d .claude`、`cp -t .claude`、`ln -s`、変数を通した指定など)。
- unit の範囲の照合は、Edit・Write だけにかかります。シェルでの書き込みは範囲の外でも止まりません。unit と inspector は、止められたら別の手段を試さないと決められていますが、これは取り決めで補っているものです。
- 他のプラグインの `PermissionRequest` の Hooks が、メインセッションへの確認に自動で答えてしまう場合があります。
- 保護パス(`.claude/` など)への書き込みでは、Claude Code 自身の確認が出て、Hooks の理由文は表示されないことがあります(実機で観測。確認は1回だけで、二重にはなりません)。
- bypassPermissions では確認の画面が出ないため、Hooks は確認の代わりに拒否を返します。保護対象のパスを含む読み取りだけのコマンド(`ls .claude` など)も止まります。
- プラグインと MCP のコマンドの照合は、`claude` を直接呼ぶ形だけです。npx、pnpm dlx、bunx、`node cli.js` などを通した起動は止まりません。~/.claude/ の下の設定やスキルを直接書き換えることも、プロジェクトの外なので照合しません。モデルからは呼べない `/plugin` は照合しません。
- 候補のスキルの SKILL.md を、計画の決心の前に Read で開かないことは、ルールだけで守らせています。開いても使用量が増えるだけで、何かが動くわけではないこと、Hooks で止めるとスキルそのものを直す仕事で読めなくなることから、Hooks では止めていません(0.3.0 の実地では、決心の前に開いた回がありました)。
- mission も mission-analysis も読み込まず、/ai-headquarters:mission でも始めずに、作戦記録を作る前にほかのスキルを読み込むことは、Hooks では止められません。mission-analysis が読み込まれたあとでも、作戦記録ができる前に、あなたの発言が3回目になってから読み込むこと(質問が3回以上続いたときなど)と、メインセッションが決まりに反して `.ai-headquarters/` の外を書き換えたあとに読み込むことは、止められません。シェルのコマンドでの書き換えでは作戦の始まりが終わらないため、そのときは、あなたの3回目の発言まで確認が出ることがあります。
- 外を探す intel の「プロジェクトのファイルを読まない」「URL に手元の情報を入れない」という制約と、外から来た文を指示として扱わない決まりは、ルールで守らせるもので、Hooks では守られません。外の文書に仕込まれた指示が、これを破らせようとすることがあります。

### 承認の限界

- UserPromptSubmit の入力に、発言の出どころを見分ける欄がありません。メッセージ全体がちょうど「承認」なら、バックグラウンドのサブエージェントの報告や別のセッションからのメッセージでも、承認として記録されることがあります。
- 作戦記録ができる前に「承認」と入力しても、記録されません。メインセッションが作戦記録を作ってから、もう一度「承認」と入力してください(承認を2回入力することがあります)。
- 大規模の節目ごとの承認は、Hooks ではなく、ルール(スキル)で守らせています。
- メインセッションが作戦記録の「目標の決心」の欄を偽って埋めれば(「省略:」と書くなど)、目標の決心を飛ばせます。これは Hooks では防げず、ルールで守らせています(省いたときは、理由が報告と作戦記録に書かれます)。
- 目標の決心を省くかどうかは、メインセッションが判断して作戦記録に書きます。Hooks は、省ける条件を本当に満たしているかまでは確かめられません。省かれたときは、任務分析の報告に書かれた理由を読み、おかしければ「承認」と入力せずに、直す点を書いてください。
- 「目標の決心」の欄が無い古い作戦記録では、最初の「承認」が目標の決心として記録されるので、unit を起動するまでに「承認」が2回要ります。
- 計画の決心の前に、メインセッションが直接ファイルを書き込まないことも、ルールで守らせています(unit の起動は Hooks で止まります)。

### 型と報告の限界

- 報告の確認は、見出しがそろっているかだけを見ます。中身の正しさは確かめません。
- 2回目は警告を付けて通します。警告は、あなたの画面に出るはずです。メインセッションのモデルには届きません(どちらも、実機で確かめる途中です)。
- auto モードで、`SubagentHandback` を呼ばずに終わったサブエージェントの報告は、確かめられずに通ります。
- 命令書の【変更してよいファイル】に、名前に `,`、`、`、` - `、`:` を含むパスや、名前の最後が括弧で終わるパスは書けません(別のパスとして読まれます)。書かずに、未解決として上げる決まりです。
- 規模判定は、モデルの判断に頼ります。3ファイル以上の簡単な変更を、小規模と判断して自分で直すことがあります(メインのモデルが Sonnet のときに起きました)。そのときは、`/ai-headquarters:mission 中` のように、規模を指定して始めてください。
- エージェントが型どおりに書くか、自動で委任されるかは、実機で測って調整する途中です。小さな調べものは、intel に任せず、メインセッションが自分で片付けることがあります。

### 環境の限界

- プロジェクトの外にあるスキルを読むときは、読む許可の確認が出ます。`claude -p` では拒否され、そのスキルは使われません。
- **`claude -p` やバックグラウンドで使うと、サブエージェントの `npm test` などのコマンドが、権限の確認を出せずに拒否されます。** 対話の画面では、確認が出ます。`-p` で使うときは、プロジェクトの `.claude/settings.json` に、テストのコマンドを許可として足してください。書き方の例です(公式の権限の説明で確かめてください)。

  ```json
  {
    "permissions": {
      "allow": ["Bash(npm test)", "Bash(npm test *)"]
    }
  }
  ```

- auto モードでは、unit が危ない操作を自分で断ることが多く、そのため Hooks が止める場面は少なくなります。

- クラウドのセッションと WSL のセッションでは、プラグインを使えないため、AI司令部は使えません(公式の文書。第5章の「デスクトップアプリだけを使っている場合」)。

- Windows に Git for Windows が入っていない環境では、Bash ツールが使えず、PowerShell ツールが使われます。Hooks は両方にかけています。PowerShell ツールが無い環境(Mac、Linux)で、`tools` の `PowerShell` が無視されるかは、確かめていません(無視されると推定しています)。
- 待ち時間:ツールを呼ぶたびに、Node.js を起動します。測定(Windows 11、Node 26)では、1回あたり約100ミリ秒で、そのほとんどが Node.js の起動です。実機での中央値は、第11章にあります。Read、Grep、Glob は Hooks を通りません。

- Windows 11 Home、Claude Code 2.1.319、Node.js v26.13.1(2026-11-19 に確認)。対話の画面での確認は、Claude Code 2.1.327 で行いました。

- Hooks の動きを確かめる自動テストは、Windows と Mac で合格しています(Node.js 22 と 24)。

**まだ確かめていないこと**

次のことは、まだ確かめていません。

- Linux での動き。
- Mac で、Claude Code の画面から使ったときの動き(Mac で合格しているのは、自動テストだけです)。Mac のデスクトップアプリでの入れ方も、まだ確かめていません。
- auto モードで、Hooks が操作を止めるときの動き(auto では、unit が危ない操作を自分で断ることが多いため)。
- 報告の差し戻しが2回目で通るとき、警告があなたの画面に出るか。
- 並列のときに止められた2体目の unit を、もう一度起動できるか。
- デスクトップアプリで入れたあとの動き(Hooks の確認や、承認の関門など)。
- 端末での更新と取り除き方。
- 大規模の作戦での資源の手配(第4部の評価の中で、案ごとに使える資源と足りない資源を見ること、plans に候補の一覧を渡すこと)。中規模では実地で確かめました。

## 12. コスト

すべて `claude -p` で、メインは sonnet(大規模の一部は opus)で測りました。1回ずつの測定で、目安です。

- 同じ課題(割引率の上限を付け、テストを足し、README に1行書く):単独は 0.106 USD、約23秒。AI司令部は 0.310 USD、約87秒(承認の往復を含む)で、費用は約3倍です。

注意点:

- 1回ずつ流した結果で、実行ごとにぶれがあります。0.2.0 を仕上げる途中の版で、目標を示さない中規模の依頼を流したときは、任務分析の回が 0.128〜0.266 USD、承認のあとの回が 0.497〜0.660 USD でした。目標の決心を足す前の大規模は 0.768 USD でした。
- 課題は完全には同じではありません。中規模の依頼は、前回の依頼(3か所の金額に「円」を付ける)に、望成目標を2つ(npm test の確認と、API から取得したレートを README に書くこと)足し、必成目標と望成目標の優先順位と損耗限度をすべて示した形にしています(目標の決心を省ける条件)。大規模は前回と同じ依頼ですが、目標の決心で、評価基準を直す点を書いています。
- 起動の設定が前回と違います。0.2.0 では、全体の設定から入っているほかのプラグインを読ませないため、`--setting-sources project,local` を付けました。前回は付けていないので、読み込む量が少し違います。
- どの回も、npm test の実行は許可していません(前回と同じ)。`-p` では権限の確認を出せないため、npm test と外部への接続は拒否されました。中規模では、2つの望成目標が損耗限度に達したとして捨てられ、最終報告に、達成に要る権限が書かれました。

目安として、マルチエージェントは万能ではありません。公開された研究では、各手順が次の手順の前提を変える作業で、性能が下がり、成功1件あたりのトークンが大きく増えた例があります。小さな仕事を単独で片付ける規模別の編成は、そのためです。

### 0.3.0 での増え方

0.3.0 で、中規模以上に第4部の資源の手配(計画書の「使う資源」)を加えました。0.2.0 と同じ条件(見本のプロジェクト、メインは sonnet、`claude -p`、目標をすべて示した同じ依頼)で、中規模を2回流しました。決心の入力ごとに別の回として流しています(費用は回ごとの値の合計です)。

| 回 | 0.3.0 | 0.2.0 |
| --- | --- | --- |
| 中規模、候補のスキルが無い | 0.736 USD(任務分析と計画 0.166 USD、承認のあと 0.570 USD) | 0.664 USD(任務分析 0.163 USD、承認のあと 0.501 USD) |
| 中規模、見本のプロジェクトに候補のスキルを1つ置いた | 1.189 USD(任務分析と計画 0.206 USD、スキルを使うと決めた回 0.259 USD、承認のあと 0.724 USD) | なし |

注意点:

- 1回ずつ流した結果で、実行ごとにぶれがあります。0.2.0 の承認のあとの回は、0.497〜0.660 USD の幅がありました。
- 候補のスキルを置いた回は、スキルを使うと決める入力が1回増えるので、決心の入力が2回になります(候補を使わないときは「承認」の1回です)。この回の承認のあとでは、計画が unit の任務を2つに分けたため、unit が2回起動しました。費用の差には、この分も含まれます。
- 候補のスキルは13行の短いものでした。長いスキルを使うと決めたときは、読む分だけ増えます(500行を超えるものは使いません)。
